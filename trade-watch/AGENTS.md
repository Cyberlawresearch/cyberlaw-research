# Trade Watch 发布规则

本目录是独立的贸易合规简报，不使用其他研究栏目的期号、新闻数量或内容模板。正文沿用 assets/style.css，历史正文保持不变。

## 每期交付

以 Asia/Shanghai 的运行日期为期日。先读取最新 main、index.html、archive.html 和最近几期完整正文，核对期号并按事件去重。新闻以过去24—72小时的新事实为依据，区分正式规则、执法决定、调查、待批准方案和政策表态。具体要求以用户最新指令为准。

每期必须实际写入以下三个文件：

- issues/YYYY-MM-DD.html：完整当期正文，来源具体到公告、规则或案件。
- index.html：最新一期入口、日期、期号和摘要。
- archive.html：新增当期入口并置顶，完整保留往期入口。

先完成来源和外部链接核验，再写当期正文，随后更新首页和归档。写入前读取目标文件当前 SHA，避免覆盖其他修改。不要提交空白页、占位页或只有标题的页面作为完成结果。

生成 HTML 时，所有 `href` 查询参数中的 `&` 必须写为 `&amp;`，避免 `&reg`、`&copy` 等片段被 HTML 解析器误识别为实体。写入后和部署后均以 DOM 解析得到的实际 URL 再做一次来源链接检查；若解析后的 URL 与原始核验 URL 不一致，必须修正后再发布。

## 使用已经验证的发布渠道

首先发现并使用已连接 GitHub 的正式工具。2026年10月1日已验证可用的路径为：fetch_file 读取 main；不存在的新正文使用 create_file；已存在的首页和归档使用 update_file，传入刚读取的 SHA 及完整 UTF-8 正文。同一路径顺序写入。不要用空白文件或无关提交测试写权限，第一次实际提交就应是完整、已核验的当期正文。

GitHub 的通用 fetch 只读取工具合同允许的 GitHub 地址。它拒绝某类地址，不能推断整个连接失效。Actions 日志使用已提供的工作流和作业日志工具，二进制证据使用工作流 artifact 下载工具。新闻原始来源使用正常网页检索、正式文件或已经获准的只读来源核验，不把来源网站读取失败混同于 GitHub 写入失败。

连接器没有实际报错时，不复述旧任务的错误作为本次结论。真实权限或安全拒绝必须如实报告，不得通过改编码、换凭据、另建执行通道或弱化检查来绕过。对正常网络、超时和服务端临时错误，可以在当前运行中重试。

## 写入和上线分开确认

每次写入后，必须用 ref=main 重新读取三个文件，核对日期、期号、新闻条数、正文和链接。只要当期正文在 main 中仍返回404，就属于尚未写入，不得解释为 Pages 刷新延迟。

检查与最终提交对应的 Pages 运行和公开页面。旧提交部署成功不能证明新一期上线。不得删除或弱化既有测试来获得成功状态，也不得为发布本目录而改写其他栏目正文。

完成标准必须同时满足：来源及法律状态已经核验；三份文件已在 main 中完整写入；对应提交的 Pages 已成功部署；当期正文、首页最新入口和归档首项的公开内容及链接核对一致；当期来源链接检查通过。单独的绿色工作流、HTTP 200、提交 SHA 或过去一期的核验记录均不构成完整发布证明。

## 按失败环节恢复

遇到报错，保留工具返回的具体信息，分别判断文件写入、Actions 构建、Pages 部署和公开页面刷新环节。没有实际报错证据时，不推断为安全检查、权限或内容校验问题。

网络超时或5xx等临时错误，首次失败后最多再试两次。写操作结果不明时先重新读取目标文件，防止重复创建。409或SHA冲突时重新读取最新 main 和目标文件，保留并发变化后只重做必要修改，不强推。已经写入的完整正文不重复生成，只续作尚未完成的入口、归档或部署步骤。

Pages 失败先读取作业及失败步骤。基础设施步骤可在当前 main 未被更新且总尝试次数不超过三次时重试。内容、结构、来源或阅读功能校验失败必须核查原因并修正相关问题，不能靠重跑或删除测试放行。旧提交被新 main 超越时，只检查并部署最新有效提交，不回滚覆盖新内容。

公开网页暂未刷新时，按最终提交重新检查正文和入口，保留实际响应及内容差异。重试仍失败，应说明尚未写入的具体文件和实际失败环节，不能把生成或提交成功称为已发布。单次失败不得关闭、暂停或删除每日任务。只有用户明确要求停止时才停止。

## 独立漏发检查

每日内容任务仍为北京时间09:00。`.github/workflows/trade-watch-release-guard.yml` 另外在北京时间10:20、14:20、20:20检查当天是否实际发布，并在 Pages 完成后检查当前提交。GitHub 调度可能排队，此检查时间不是准点送达保证。

`scripts/trade_watch_presence.py` 按北京时间当天日期检查三份文件、期号、日期、条数和公开页面，不能把首页仍显示的昨天作为今天的预期。`--latest --offline` 仅用于代码变更后的预检，不是当天发布验收。`scripts/test_trade_watch_presence.py` 覆盖缺正文、旧入口、缺归档、占位页、条数不符、公开页面不可访问及旧版本等情形。

漏发或验收失败会在 GitHub 创建或更新当日唯一的“Trade Watch 发布异常”Issue，恢复后经公开核验关闭。实际通知送达依 GitHub 账号设置。只有基础设施步骤失败才按次数限制请求 Pages 重跑，其他失败保留证据。检查器不生成新闻、不替代事实核验、不修改读者页面，也不关闭定时内容任务。

既有 `.github/workflows/trade-watch-source-check.yml` 继续核验部署后的页面和当期外部来源链接。诊断材料保存在 Actions 日志和 artifacts，不放入读者页面。内容任务应读取当前日期、当前提交对应的核验结果，不能把代码测试或旧期检查成功当作当期上线。


## 发布故障证据与任务状态

发布任务只有在实际调用 GitHub 写入工具并收到明确错误返回后，才能判断为 GitHub API、权限或安全拒绝。若没有 create_file / update_file 等真实写入调用的错误结果，不得写“平台安全检查拒绝”“权限不足”“GitHub 拦截”等结论；此时只能说明“尚未完成实际写入”并继续定位执行中断点。

当天研究草稿已存在且 publication_ready=true 时，发布任务必须首先尝试写入完整当期正文。若该写入失败，需把本次发布尝试的时间、阶段、实际工具名称、目标路径、错误码/错误文本、重试次数以及 main 中当期文件是否存在，写入 trade-watch-drafts 分支当天 JSON 的 publication_attempt 字段后再结束。若写入结果不明，先回读目标路径确认，不得仅凭模型判断宣称失败原因。

内容任务不得调用定时任务管理接口来关闭、暂停、删除或改变自身以及配套研究任务。任务启停仅响应用户明确要求。单次发布失败只记录故障并等待下一次正常调度或用户手动重跑，不改变 enabled 状态。
